## 1. 概述

### 1.1 背景与动机

Qube 是一家金融交易行业公司（外汇/CFD 经纪业务），核心系统为 MT4/MT5 交易平台 + CRM。当前业务运营存在四类核心诉求：

1. **销售数据割裂**：MT4、MT5、CRM 数据分散，入金/出金/FTD/净留存等核心指标依赖人工汇总，日报/周报/月报靠手工制作，业绩排行更新滞后。
2. **跨部门运营黑盒**：风控、出入金、合规、市场等部门的日常节点与流转效率不可见，出入金延迟、风控预警、客诉、流程卡顿等问题靠人传人发现，响应慢。
3. **客服与社群人力瓶颈**：开户、交易规则、出入金等高频咨询重复度高，多语言 24/7 响应难；社群情绪、违规内容、资讯推送缺乏自动化。
4. **SEO 与营销低效**：关键词挖掘、竞品分析、内容生产、客户分群与广告投放优化缺乏系统化工具，获客 CVR 与 ROI 有提升空间。

本项目的目标不是采购单点工具，而是为 Qube 设计并落地一套 **AI-Native 的企业级部署方案**：以 AI 为数据采集、识别、生成与决策的核心引擎，覆盖**对外上万级客户触达**与**对内全团队日常使用**两个维度。

### 1.2 目标

**业务目标**
- 核心经营指标（入金量、出金量、FTD、净留存、交易手数）实现 T+0 自动化追踪，日报/周报/月报 100% 自动生成。
- 出入金延迟、风控预警、客诉等异常从"事后发现"变为"分钟级识别并推送"。
- 客服首响时间降至秒级，AI 独立解决率 ≥ 60%，人工客服聚焦复杂问题。
- SEO 自然流量与广告 ROI 在 6 个月内可量化提升。

**用户目标**
- 管理层：一屏看清全公司经营与风险状况。
- 销售团队：实时看到个人/办公室业绩排名与转化漏斗。
- 运营/风控/合规：异常自动找上门，而非人肉巡检。
- 客服/市场团队：AI 承担重复劳动，人做判断与创意。
- 外部客户：获得 24/7 多语言即时服务与有价值的社群内容。

**成功指标（北极星指标 + KPI）**

| 指标 | 基线（现状） | 6 个月目标 |
|------|------------|-----------|
| 经营日报自动化率 | ≈0% | 100% |
| 核心指标数据延迟 | T+1 或更久 | ≤ 15 分钟 |
| 异常识别到通知的时长 | 小时级/天级 | ≤ 5 分钟 |
| 客服首次响应时间 | 分钟级（工作时间外无响应） | ≤ 10 秒，24/7 |
| AI 客服独立解决率 | 0% | ≥ 60% |
| SEO 自然搜索流量 | 待测基线 | +30% |
| 广告获客 CVR | 待测基线 | +15% |

### 1.3 范围

**本期包含（v1.0–v1.2）**
- 板块一：销售数据分析与绩效大盘（数据打通 + 指标体系 + 看板 + 自动报告 + 排行 + 异动预警）
- 板块二：跨部门日常管理与风险监测（流程穿透 + 异常/瓶颈预警 + AI 简报）
- 板块三：客服与社群智能运营（AI 客服 + 知识库 + 人机协同 + 社群监测与推送）
- 板块四：SEO/GEO 与数字营销智能化（关键词/竞品分析 + AI 内容 + 营销自动化 + 效果归因）
- 平台级：统一权限与审计、模型网关与成本管控、私有化部署架构

**本期不包含（Won't Have this time）**
- 自研基础大模型训练（采用商用 API + 开源模型私有化组合）
- 自动交易执行/代客下单（合规红线，仅做分析与预警）

- MT4/MT5 服务端本身的改造（仅通过官方 API 与报表接口读取数据）

## 2. 用户画像

**角色 A：管理层（CEO/COO/区域负责人）**
- 身份：公司经营与风险的第一责任人
- 核心目标：实时掌握全公司经营大盘与重大异常
- 主要痛点：数据靠层层汇报，滞后且口径不一；异常往往由客户先发现

**角色 B：销售团队（Sales/IB 客户经理/销售主管）**
- 身份：一线获客与客户资产运营人员
- 核心目标：看清自己的业绩、转化率与排名，知道该追哪些客户
- 主要痛点：业绩数据月底才知道；FTD、净留存靠财务手工算

**角色 C：运营/风控/合规人员**
- 身份：出入金审核、风控监控、合规检查的执行者
- 核心目标：异常单自动浮现、优先处理高风险事项
- 主要痛点：每天人肉刷系统巡检；跨系统切换效率低；问题升级为客诉才被重视

**角色 D：客服团队（CS 专员/主管）**
- 身份：多语言客户服务一线
- 核心目标：减少重复咨询负担，把精力放在复杂问题与高危客户上
- 主要痛点：80% 问题是重复的开户/出入金/规则咨询；夜间与节假日无人值守

**角色 E：市场团队（Marketing/SEO/投放）**
- 身份：内容生产、SEO、广告投放与社群运营人员
- 核心目标：内容生产效率倍增，投放 ROI 可衡量可优化
- 主要痛点：关键词与竞品分析靠手工；内容产出慢；客户分群粗放

**角色 F：外部客户（交易者，上万规模）**
- 身份：Qube 平台的新老客户
- 核心目标：随时获得准确的开户/交易/出入金帮助与有价值的行情内容
- 主要痛点：咨询响应慢、非工作时间无人理、社群信息噪音大

## 4. 总体架构与工具选型（AI-Native 部署方案）

### 4.1 设计原则

1. **AI-Native，而非"系统 + AI 补丁"**：数据采集、异常识别、内容生成、问答应答全部由 AI 驱动；人负责审核、决策与例外处理。
2. **数据先行**：四大板块共用同一个数据底座（数据仓库 + 指标体系），避免四套系统四套口径。
3. **开源优先、商业补位**：优先采用 GitHub 上成熟、社区活跃的开源项目（自托管、可二次开发、数据不出域）；开源明显薄弱的环节（SEO 深度数据、MT4/MT5 接入）诚实标注并采用官方/商业方案。
4. **私有化/VPC 部署**：金融数据敏感性要求所有核心组件支持自托管，客户数据不出企业边界。
5. **对内/对外一套底座两套门面**：同一数据与 AI 基座，对内是管理与分析门户，对外是客户服务与触达通道。

### 4.2 总体架构分层

```
┌─────────────────────────────────────────────────────────────┐
│ L5 触达层                                                    │
│ 对内：管理门户 / 大屏 / 移动端推送 / 邮件 & IM 机器人          │
│ 对外：官网客服挂件 / WhatsApp / Telegram / 社群 / 邮件 / SEO站点│
├─────────────────────────────────────────────────────────────┤
│ L4 业务应用层                                                │
│ 绩效大盘(Superset) │ 运营监控(Grafana/Nightingale)            │
│ 客服工作台(Chatwoot) │ 营销自动化(Mautic) + 分析(PostHog)      │
│ SEO/内容工作台(Dify + 自研审核流)                              │
├─────────────────────────────────────────────────────────────┤
│ L3 AI 能力层                                                 │
│ Agent/工作流编排：Dify · n8n                                  │
│ 知识库 RAG：RAGFlow / FastGPT                                 │
│ 模型网关：LiteLLM / GoModel（商用 API + 本地开源模型统一接入） │

│ 客服会话 │ 网站/落地页埋点 │ 广告平台 │ 社群 IM │ SEO 工具     │
```

### 4.3 板块一解决方案：销售数据分析与绩效大盘

**方案概述**：MT4/MT5/CRM 三源数据 → Airbyte + 自研 MT4/MT5 适配器 → ClickHouse 数据仓库 → dbt 统一指标口径 → Superset 绩效大盘 + 自动报告 + 异动预警。

| 环节 | 选型 | GitHub 成熟度（2026-08-08） | 选型理由 |
|------|------|---------------------------|----------|
| 数据集成（ELT/CDC） | **Airbyte** `airbytehq/airbyte` | ⭐ 21,841 · forks 5,292 · 活跃维护 | 300+ 连接器，支持 CDC，自托管，覆盖 CRM（MySQL/PostgreSQL/SQL Server）与各类 SaaS |
| MT4/MT5 接入 | **官方 MetaQuotes Manager API / Web API / 定时报表导出 + 自研适配器** | 无成熟开源桥接（检索到的 MT5 开源项目均 < 20★，不可用于生产） | 金融行业严肃场景必须用官方接口；适配器负责定时抽取交易/账户快照入仓 |
| 数据仓库（分析型） | **ClickHouse** | 业界主流 OLAP（上万级客户交易明细的高并发聚合场景标配） | 交易流水体量大、聚合查询多，列式仓库性能远优于 MySQL |
| 指标建模 | **dbt** | 数据建模事实标准 | 把"入金量/FTD/净留存"等指标口径代码化、版本化，杜绝各部门口径打架 |
| BI 大盘/可视化 | **Apache Superset** `apache/superset` | ⭐ 74,178 · forks 18,067 · Apache 顶级项目 | 企业级 BI，支持行级权限（RLS）、SQL Lab、多数据源，适合"管理大盘 + 办公室排行" |
| BI 备选（轻量/嵌入式） | **Metabase** `metabase/metabase` ⭐ 48,595；**DataEase** `dataease/dataease` ⭐ 24,303 | 均活跃 | 若需嵌入自有门户或中文体验优先，可二选一；建议以 Superset 为主 |
| AI 报表（中文场景增强） | **积木报表 JimuReport** `jeecgboot/jimureport` | ⭐ 8,153 · 活跃 | "一句话生成报表/大屏"、对话式改报表，适合业务人员自助做报表，作为 Superset 的补充 |
| 异动预警 | **Grafana** `grafana/grafana` + 自研 AI 异常检测服务 | ⭐ 76,153 · CNCF 生态 | 阈值告警成熟；叠加 LLM 对异动做"原因初判与解读"后推送 |

**关键产出物**
- 绩效大盘（管理层/销售/办公室三级视图）
- 日报/周报/月报：定时任务生成 → LLM 撰写"异动解读与摘要" → 邮件/IM 推送
- Sales Ranking / Office Ranking：基于 dbt 指标层自动计算，每日刷新

### 4.4 板块二解决方案：跨部门日常管理与风险监测

**方案概述**：各部门系统与工单节点事件化 → 事件流 → 规则引擎 + LLM 异常识别 → 分级告警（IM/邮件/电话升级）→ 管理层 AI 简报。

| 环节 | 选型 | GitHub 成熟度 | 选型理由 |
|------|------|--------------|----------|
| 流程编排与自动化 | **n8n** `n8n-io/n8n` | ⭐ 199,757 · forks 59,999 · 极其活跃 | 400+ 集成，原生 AI 节点（可内嵌 LLM 判断步骤），自托管，是把"节点监控 + 异常识别 + 通知"串起来的最佳编排器 |
| 监控与告警 | **Grafana** ⭐ 76,153 + **夜莺 Nightingale** `ccfos/nightingale` ⭐ 13,223 | 均活跃 | Grafana 做可视化与阈值告警；夜莺补充告警事件管理与值班分派（中文团队友好） |
| 日志/事件汇聚 | **OpenObserve** `openobserve/openobserve` | ⭐ 20,592 · 活跃 | 单二进制部署、低存储成本的日志/指标/链路平台，承接各部门系统事件流 |
| 异常与瓶颈识别 | **自研 AI 服务（LLM + 规则）**：出入金超时识别、流转卡顿检测、客诉聚类 | 该细分领域无成熟专用开源（2026-08-08 检索证实），用 n8n + LLM 编排实现 | "超时未处理""同一客户多次往返""投诉关键词聚类"等模式用规则+LLM 双保险 |
| AI 简报 | **Dify 工作流**（定时拉取异常清单 → LLM 生成管理层简报） | 见 4.6 | 与板块三共用 AI 基座 |

**典型场景**：出入金申请创建 → 节点事件入 OpenObserve → n8n 定时巡检：超过 SLA 未处理 → LLM 判断紧急度并生成摘要 → 按级别推送（专员 IM → 主管 → 管理层）。

### 4.5 板块三解决方案：客服与社群智能运营

**方案概述**：Chatwoot 作为全渠道客服工作台 → Dify/RAGFlow 提供 AI 应答与知识库 → 人机协同转接 → 社群侧用 LangBot 接入 IM，做情绪监测、违规过滤与资讯推送。

| 环节 | 选型 | GitHub 成熟度 | 选型理由 |
|------|------|--------------|----------|

### 4.8 部署架构与容量规划（上万外部用户 + 内部团队）

**用户规模拆解**
- 对内：管理层 + 销售 + 运营/风控/合规 + 客服 + 市场，预估 100–500 人，高峰并发 < 100。
- 对外：上万客户的触达面 = 官网客服挂件会话、社群机器人消息、邮件触达、SEO 站点访问。**外部客户不直接进入数据大盘**（安全隔离），只通过客服/社群/邮件/网站与系统交互。

**部署拓扑（私有化/VPC，Kubernetes）**

| 分区 | 内容 | 说明 |
|------|------|------|
| DMZ（对外区） | 官网/落地页、Chatwoot 挂件网关、LangBot Webhook 入口、WAF | 对外唯一入口，反向代理 + 限流 |
| 应用区（对内） | Superset、Chatwoot 工作台、Mautic、PostHog、Dify、n8n、RAGFlow | 仅企业 VPN/SSO 可达 |
| 数据区 | ClickHouse、PostgreSQL、Redis、OpenObserve、向量库 | 不出内网；备份与容灾 |
| AI 区 | 模型网关、本地模型推理节点（GPU 服务器 ×1–2，可选）、AI 异常检测服务 | 敏感任务本地推理，其余走商用 API |
| 办公接入 | SSO（Keycloak/企业 IdP）+ RBAC + 审计日志 | 对内所有系统统一登录与权限 |

**容量估算（上万客户量级）**
- 客服 AI 应答：峰值按 200 并发会话估算，Dify 无状态水平扩展 + 网关限流；本地 GPU 节点仅承接敏感任务，常规问答走商用 API。
- 数据量：MT4/MT5 交易流水按客户数 × 日均笔数估算，ClickHouse 单节点起步（SSD + 64GB RAM 可支撑千万级行/日），后续按分片扩展。
- 可用性目标：对内系统 99.5%，对外客服通道 99.9%（AI 应答故障时降级为留言 + 人工回呼）。

**灾备与安全**
- 数据仓库每日快照 + 跨机房备份；客服知识库与配置文件纳入 Git 版本管理。
- 全链路审计：谁在何时看过什么客户数据、AI 回答了什么，全部留痕（金融合规）。
- 权限三域隔离：外部客户域 / 内部业务域 / 数据与运维域。

## 7. 验收标准

> 格式：Given-When-Then。Must 功能 ≥3 条（正常/异常/边界），Should ≥2 条，Could ≥1 条。

### F-001 MT4/MT5 数据接入
- AC-F001-01：Given MT4/MT5 官方接口凭证有效，When 到达抽取周期，Then 账户、出入金、交易流水按时入仓且记录数与源系统对账一致（误差 = 0）。
- AC-F001-02：Given 接口凭证失效或网络中断，When 抽取失败，Then 系统记录失败日志、按指数退避重试，并在连续 3 次失败后向运维告警，不污染已有数据。
- AC-F001-03：Given 单笔交易字段缺失或格式异常，When 清洗时遇到该记录，Then 该记录进入隔离区并计数告警，正常记录不受影响。

### F-002 CRM 数据接入与合并
- AC-F002-01：Given CRM 数据库可连接，When CDC 同步运行，Then 新增/变更客户在 15 分钟内同步并与交易数据按客户 ID 正确关联。
- AC-F002-02：Given CRM 中同一客户存在重复档案，When 合并时，Then 按预定义主档规则合并并保留合并日志，可追溯。
- AC-F002-03：Given 客户无归属销售/办公室，When 生成归属报表时，Then 该客户归入"未分配"桶单独展示，不产生错挂。

### F-003 核心指标体系
- AC-F003-01：Given 指标口径已在 dbt 定义，When 计算入金量/出金量/FTD/净留存/交易手数，Then 同一指标在大盘、报告、排行三处数值完全一致。
- AC-F003-02：Given 口径需要调整，When 修改 dbt 模型，Then 变更经评审后生效、历史数据重算有记录，口径版本可追溯。
- AC-F003-03：Given 跨币种入金，When 计算净留存，Then 按配置汇率统一折算并标注汇率来源与日期。

### F-004 绩效大盘可视化
- AC-F004-01：Given 用户有对应角色权限，When 打开大盘，Then P95 ≤ 3 秒加载完成，展示与其角色匹配的视图（管理层/销售/办公室）。
- AC-F004-02：Given 销售 A 登录，When 查看排行，Then 只能看到自己及授权范围内数据（行级权限生效）。
- AC-F004-03：Given 数据仓库延迟或不可用，When 打开大盘，Then 页面明确显示数据截至时间并提示延迟，不展示空白误导。

### F-005 自动日报/周报/月报
- AC-F005-01：Given 到达配置时间，When 报告任务触发，Then 自动生成含核心指标与 LLM 异动解读的报告，并推送至配置的邮件/IM，接收人可正常打开。
- AC-F005-02：Given LLM 服务不可用，When 生成报告，Then 降级为纯数据报告（无异动解读段）并标注"AI 解读暂缺"，报告仍按时送达。
- AC-F005-03：Given 节假日无交易，When 生成日报，Then 报告正常生成并标注休市，不产生异常告警。

### F-006 数据异动预警
- AC-F006-01：Given 指标突破阈值或被 AI 判定异常，When 异常发生，Then 5 分钟内按级别推送责任人，内容含指标、偏离度与 LLM 原因初判。
- AC-F006-02：Given 同一异常持续存在，When 告警已发出且未恢复，Then 按配置频率提醒升级（专员→主管→管理层），不每分钟重复轰炸。
- AC-F006-03：Given 告警规则配置错误（如阈值 = 0），When 保存配置，Then 系统校验并拒绝非法配置并提示原因。

### F-007 Sales Ranking
- AC-F007-01：Given 当月业绩数据已入仓，When 到达每日刷新时间，Then 个人业绩与转化率排行自动更新，与指标层数值一致。
- AC-F007-02：Given 某销售月中离职/转岗，When 生成排行，Then 按配置的归属规则处理历史业绩并在页面说明。
- AC-F007-03：Given 月初无业绩，When 查看排行，Then 展示"暂无数据"空态而非报错或显示上月数据。

### F-011 工作流节点监控
- AC-F011-01：Given 部门系统产生节点事件，When 事件上报，Then 流转面板实时展示单据当前节点与停留时长。
- AC-F011-02：Given 某部门系统接口中断，When 事件停发，Then 监控面板标记该来源"数据中断"并告警，不误判为"无单据"。
- AC-F011-03：Given 单据跨部门流转，When 查看流转轨迹，Then 完整呈现经手部门、节点与耗时。

### F-012 出入金延迟预警
- AC-F012-01：Given 出入金申请超过 SLA 未处理，When 超时发生，Then 自动向处理人与主管推送预警，含单据信息与已等待时长。
- AC-F012-02：Given 单据在超时前已完成，When SLA 计时结束，Then 不产生预警。
- AC-F012-03：Given 紧急大额出金（超过配置金额），When 创建时，Then 立即标记加急并通知，不等 SLA 超时。

### F-013 风控预警聚合推送
- AC-F013-01：Given 多个系统同时产生预警，When 进入告警中心，Then 同源重复预警自动去重聚合，按严重度排序展示。
- AC-F013-02：Given 高危预警（如监管相关），When 产生时，Then 立即推送管理层并电话/强提醒升级（按配置）。
- AC-F013-03：Given 预警被误报，When 责任人标记误报，Then 记录处置人与理由，进入误报统计供规则优化。

### F-017 全渠道客服接入
- AC-F017-01：Given 客户从官网挂件/WhatsApp/Telegram/邮件任一发消息，When 消息到达，Then 统一进入客服收件箱并保留来源渠道标识。
- AC-F017-02：Given 某渠道接口故障，When 客户发消息，Then 系统自动降级提示客户改用其他渠道并告警运维，消息不丢失。
- AC-F017-03：Given 同一客户跨渠道咨询，When 客服打开会话，Then 展示该客户跨渠道历史记录（按客户身份合并）。

### F-018 AI 客服自动应答
- AC-F018-01：Given 客户用中文/英文/支持的语种提问高频问题，When AI 应答，Then 首 token ≤ 3 秒，答案引用知识库来源且内容一致。
- AC-F018-02：Given 问题超出知识库范围或置信度低，When AI 判断，Then 不编造答案，按策略转人工或回复"需人工确认"并建单。
- AC-F018-03：Given 非工作时间，When 客户提问，Then AI 正常应答，转人工请求进入次日优先队列并告知客户预期响应时间。

### F-019 金融知识库 RAG
- AC-F019-01：Given 运营上传开户/规则/出入金文档，When 入库完成，Then 相关提问可被准确检索且答案附文档引用。
- AC-F019-02：Given 制度文档更新（如出入金政策变更），When 重新入库，Then 旧版本失效，AI 回答只引用最新版本。
- AC-F019-03：Given 文档包含矛盾条款，When 入库或抽检，Then 系统提示矛盾点供人工处理，不静默二选一。

### F-020 人机协同转接
- AC-F020-01：Given 命中转人工条件（低置信/敏感词/客户要求），When 转接发生，Then 人工坐席收到完整会话上下文与 AI 摘要，客户无需重复描述。
- AC-F020-02：Given 无坐席在线，When 转接请求产生，Then 自动建工单并告知客户预期响应时间，不显示"无限等待"。
- AC-F020-03：Given 会话结束，When 审计抽查，Then 可调取完整记录（客户消息、AI 回答、引用来源、人工处置）。

### F-025 AI 内容生产流水线
- AC-F025-01：Given 选题与关键词输入，When 工作流运行，Then 产出大纲与初稿，进入"待合规审核"状态，未经人工审核通过不可发布。
- AC-F025-02：Given 审核人驳回稿件，When 驳回时填写意见，Then 稿件退回 AI 修改环节并保留版本历史。
- AC-F025-03：Given 内容含收益承诺等违禁表述，When 自动合规检查运行，Then 标记风险并阻止进入发布队列。

### F-029 客户分群与营销自动化
- AC-F029-01：Given CRM 客户数据已同步，When 执行分群规则（如"注册 7 天未入金"），Then 分群结果与数据仓库口径一致并可导出清单。
- AC-F029-02：Given 邮件旅程已配置，When 客户进入分群，Then 按旅程自动触达，发送、打开、点击数据回流可统计。
- AC-F029-03：Given 客户退订，When 收到退订请求，Then 立即停止该客户一切营销触达并记录合规留痕。

### F-032 统一权限与审计
- AC-F032-01：Given 员工使用 SSO 登录，When 访问任一对内系统，Then 权限与其角色一致，越权访问被拒绝并记录。
- AC-F032-02：Given 外部客户，When 尝试访问对内系统地址，Then 网络层不可达（DMZ 隔离）。
- AC-F032-03：Given 员工离职，When HR 状态变更，Then 其全部系统权限在 24 小时内自动回收。

### F-033 模型网关与成本管控
- AC-F033-01：Given 任一 AI 功能发起模型调用，When 调用发生，Then 请求必经网关，按调用方记账，成本报表可按板块/功能拆分。
- AC-F033-02：Given 调用涉及客户敏感数据（交易记录/身份信息），When 路由决策，Then 强制走本地模型，不经任何外部 API。
- AC-F033-03：Given 某模型供应商故障或超时，When 调用失败，Then 网关自动切换备用模型并记录，业务无感知。

### F-008 Office Ranking
- AC-F008-01：Given 各办公室归属数据完整，When 刷新排行，Then 跨区域业绩与协同对比正确展示，与指标层一致。
- AC-F008-02：Given 某办公室数据缺失，When 展示排行，Then 该办公室标记"数据缺"并说明，不影响其他办公室排名。

### F-009 热门/异常品种分析
- AC-F009-01：Given 交易流水入仓，When 执行品种聚合，Then 热门品种榜单与异常品种标记每日更新。
- AC-F009-02：Given 某品种成交异常放大，When 检测触发，Then 生成异常记录并通知风控。

### F-014 客诉智能识别与升级
- AC-F014-01：Given 会话中出现投诉意图或强烈负面情绪，When AI 分类，Then 自动生成客诉工单并升级通知主管。
- AC-F014-02：Given 客户表达不满但未构成投诉，When AI 分类，Then 标记"关注"而不建单，避免工单泛滥。

### F-015 管理层 AI 简报
- AC-F015-01：Given 当日存在异常与瓶颈记录，When 到达推送时间，Then 生成含异常摘要、影响与建议的简报推送管理层。
- AC-F015-02：Given 当日无异常，When 生成简报，Then 推送"无异常"简报而非空白或缺发。

### F-021 社群情绪监测
- AC-F021-01：Given 群消息持续流入，When 情绪分类运行，Then 情绪面板按群/时间维度更新。
- AC-F021-02：Given 负面情绪短时聚集（超过配置阈值），When 触发，Then 实时预警社群负责人。

### F-022 违规内容过滤
- AC-F022-01：Given 消息命中违规（广告/诈骗/敏感词），When 检测到，Then 按策略处置（撤回/警告/人工复核）并记录。
- AC-F022-02：Given 误过滤发生，When 管理员申诉复核，Then 恢复内容并反馈优化分类器。

### F-023 资讯与行情推送
- AC-F023-01：Given 新资讯或定时行情任务，When 生成内容，Then 经审核规则后按客户分层推送，推送数据可统计。
- AC-F023-02：Given 资讯源不可用，When 任务运行，Then 跳过该次并告警，不推送过期内容。

### F-026 关键词挖掘与竞品分析
- AC-F026-01：Given 种子词与竞品域名，When 定期任务运行，Then 产出关键词机会清单与竞品内容策略摘要。
- AC-F026-02：Given 商业数据源配额用尽，When 任务运行，Then 明确提示配额状态并保留上次结果，不输出残缺报告。

### F-027 技术 SEO 审计
- AC-F027-01：Given 站点 URL 配置完成，When 定期审计，Then 输出性能、索引、结构问题清单及修复优先级。
- AC-F027-02：Given 站点临时不可达，When 审计运行，Then 记录失败原因并告警，不产生误导性"健康"结论。

### F-030 投放效果归因
- AC-F030-01：Given 埋点与广告数据齐备，When 查看归因报表，Then 渠道→注册→FTD 漏斗与 CVR/ROI 与经营报表口径一致。
- AC-F030-02：Given 某渠道埋点缺失，When 展示报表，Then 该渠道标记"数据不全"，不硬算 ROI。

### F-034 多语言支持
- AC-F034-01：Given 用户切换语言，When 使用系统，Then 界面与 AI 应答均以所选语言呈现。
- AC-F034-02：Given 某语种翻译缺失，When 展示，Then 回退英文并记录缺失项，不出现乱码。

### F-010 / F-016 / F-024 / F-028 / F-031（Could，各 1 条）
- AC-F010-01：Given 业务人员用自然语言提问（如"上月各办公室 FTD 对比"），When 系统处理，Then 返回与指标层一致的数据答案或明确"无法回答"。
- AC-F016-01：Given 流程数据积累 ≥ 30 天，When 运行瓶颈分析，Then 输出各环节流转时长分位数与 TOP 卡顿环节。
- AC-F024-01：Given CRM 标签与社群关联配置，When 执行分群运营任务，Then 不同分群收到差异化内容。
- AC-F028-01：Given 品牌关键词集，When 定期向 AI 引擎提问，Then 记录品牌被引用情况并生成 GEO 优化建议报告。
- AC-F031-01：Given 落地页实验配置完成，When 流量分配运行，Then 各版本数据隔离统计，实验结论可导出。

## 8. 执行计划（落地路线图）

### 8.1 总体节奏

> 总周期约 26 周（6 个月），四个阶段递进，每阶段有可独立验收的交付物。数据底座先行，对内管理先行，对外触达随后——风险最高的数据接入放在最前面做。

### Phase 0：奠基与审计（第 0–2 周）

| 工作项 | 交付物 | 责任方 |
|--------|--------|--------|
| 需求确认会：与管理层/销售/运营/客服/市场逐板块对齐本 PRD | 签字确认的范围基线 | 双方 |
| 数据接入审计：MT4/MT5 版本与接口权限、CRM 库结构、各渠道账号盘点 | 数据接入可行性报告 | 数据工程 + Qube IT |

## 9. 假设与约束

### 9.1 假设

1. Qube 拥有 MT4/MT5 白标或自有服务器，能申请到官方 Manager API / Web API 权限。
2. CRM 数据库可被直接读取（或提供只读副本/导出接口）。
3. "上万外部用户"指客服/社群/邮件触达面，而非直接进入 BI 系统的并发用户；外部客户不直接登录对内系统。
4. Qube 接受私有化/VPC 部署模式，并能提供或采购相应基础设施。
5. 营销内容发布遵循"AI 初稿 + 人工合规审核"流程，Qube 有合规人员承担审核。
6. 客服知识库所需的制度文档（开户流程、交易规则、出入金政策）由 Qube 提供并保持更新。
7. 业务覆盖多语言地区，首期以中文 + 英文为主。

### 9.2 约束

- 技术约束：MT4/MT5 无成熟开源数据桥接（2026-08-08 GitHub 检索确认），必须走官方接口 + 自研适配器，进度受其权限审批影响。
- 合规约束：不触碰自动交易执行；客户敏感数据不出企业边界（敏感 AI 任务本地推理）；营销内容人工审核后方可发布。
- 生态约束：开源 SEO 深度数据工具整体薄弱，关键词/外链深度数据依赖商业 API 预算。
- 渠道约束：WhatsApp Business API 等官方通道审核周期不可控。

### 9.3 风险登记

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|---------|
| MT4/MT5 API 权限审批延迟 | 高 | 中 | Phase 0 即启动申请；准备报表导出兜底方案（T+1 数据先行） |
| 数据口径与历史报表打架 | 高 | 中 | 指标层与财务联合评审；上线初期双轨运行 2 周对账 |
| AI 客服答错金融问题引发客诉/合规风险 | 高 | 中 | 知识库引用溯源、低置信强制转人工、敏感话题硬规则拦截、全程留痕审计 |
| 商用 LLM 成本随用户量失控 | 中 | 中 | 网关按任务路由（轻任务用轻模型）、限流与预算告警、成本报表周审 |
| 开源组件版本维护与二开成本 | 中 | 中 | 选型均为高活跃度项目（检索验证）；控制二开深度，优先配置化 |
| 社群违规内容误判引发用户不满 | 中 | 低 | 先"标记 + 人工复核"模式运行 4 周再放开自动处置 |
| 上万客户触达触发渠道封号（IM/邮件） | 中 | 中 | 官方通道资质齐全、发送频率控制、多通道冗余 |
